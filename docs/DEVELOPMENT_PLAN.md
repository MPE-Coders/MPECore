# MPECore: от подтверждённого входа к игровому серверу

Обновлено 26.09.2026. Это план реализации, а не список обещанной совместимости.

## Подтверждённая отправная точка

Владелец проекта сообщил об успешном входе официальным Minecraft Bedrock
1.26.20. Доступен ограниченный Creative и плоская площадка. Это пользовательский
плейтест, не автоматическая сертификация всех клиентов, платформ и механик.
Ранее CI проверил зашифрованные loopback-сессии с тестовой offline-идентичностью
на 975, 1001 и 2193. Официальный вход 1.26.51 ещё не подтверждён.

Мир/позиции/проверки блоковых действий и журнал находятся в Rust. Сетевые
сессии, инвентарь текущего Creative и Plugin API пока находятся в PHP;
2193 дополнительно использует Node-кодек. Это переходная архитектура,
не полностью независимый Rust-сервер. Новые игровые системы проектируем
с единственным владельцем состояния в Rust, сохраняя простой PHP API.

## Сейчас: P0 — устранение блокеров и лагов строительства

Реализованы в текущем изменении:
- выбор Node >=24 или установка закреплённого Node 24.21.0 в .runtime/node
  без изменения системного Node и shell-профилей;
- UpdateBlock больше не помечает загруженный чанк незагруженным;
- содержательно адресуемый кеш чанков не очищается целиком при каждом изменении;
- сетевой regression-тест требует отсутствие LevelChunk для изменённого столбца
  после обычной установки/разрушения; другие начальные чанки не учитываются;
- `/mpe perf` показывает счётчики отправленных в очередь пакетов и время
  от передачи игрового действия в Rust до его ответа (последние 256 действий).

До правки новый сетевой тест ловил 2 повторных LevelChunk на пару установка /
разрушение; после правки ожидает 0 и по-прежнему проверяет состояние Rust.
Это не обещание нулевой задержки или заданного числа игроков.

Оставшиеся P0-проверки: игра человеком на 1.26.20 и 1.26.51, строительство
сериями, отрицательные координаты и границы чанков, прыжки/полёт, повторный
вход, исправление отклонённых клиентских предсказаний, штатная остановка
и восстановление после сбоя. Сохраняем реальные логи и точный commit.

`sync_data()` на изменение пока остаётся: ACK не должен означать сохранность,
если данные фактически остались только в памяти. При измеренном дисковом
узком месте следующий шаг — отдельный storage-worker с ограниченной очередью
и групповым подтверждением записи. Нужны порядок операций, обработка ошибки
диска и backpressure, а не просто отключение fsync. Синхронный JS codec bridge
также требует измерения и последующей замены/пакетной обработки.

## Последовательность этапов и условия приёмки

| Этап | Реализация | Проверяемый результат |
|---|---|---|
| P0. Стабильный Creative | Запуск, инкрементальные обновления, диагностика, исправление входа/движения | Официальный клиент ставит и ломает блоки без принудительной пересылки чанка; изменения переживают перезапуск |
| P1. Полноценная модель мира | StateId(u32), реестры, единый ChunkStore, миграция IPC и WAL, формы столкновения | Генерация, чтение блока, столкновения, сохранение и сеть читают одно состояние; старые тестовые карты мигрируются на копии |
| P2. Базовый мультиплеер | PlayerList/скины/AddPlayer/RemoveActor, область видимости, движение, экипировка | Два официальных клиента видят друг друга и одинаковые изменения; выход/повторный вход не оставляют призраков |
| P3. Игровые предметы и Survival | Режимы, здоровье/урон/смерть, инвентарь, добыча/дроп/подбор, крафт, верстак, печь, сундук | Дерево → верстак → инструмент → руда → печь → сундук; после перезапуска нет потерь и дублирования |
| P4. Обычный Overworld | Высоты/биомы/пещеры/руды/деревья, освещение/вода и детерминированные стадии чанка | Один seed даёт те же чанки независимо от порядка и числа потоков; нет швов и расхождения видимого мира с коллизиями |
| P5. Расширенные механики | Мобы/AI, структуры/деревни, редстоун, Nether/End/порталы/дракон | Каждая подсистема имеет отдельные тесты и игровую приёмку, а не только зарегистрированный ID |
| P6. Эксплуатация и расширяемость | Снимки/компактация/резервирование, права/команды/бан-лист, версии API, bounded plugin jobs | Рабочая установка обновляется с резервной копией и проверяемой миграцией; неисправный плагин не повреждает мир |

P1 предшествует полному импорту состояний и новому генератору. P2 и базовая
часть P3 могут развиваться отдельно после фиксации контрактов P1. P4 исследуется
параллельно, но не должен блокировать P0/P2 и незаметно менять старые карты.
Не называем выпуск 1.0 только по количеству файлов или зелёным unit-тестам.

## Все блоки и предметы: реестр не равен поведению

Сначала устраняем однобайтовые внутренние ID. Внешние runtime ID остаются
отдельными для каждого протокола. Типизированные NBT-свойства, идентификатор
предмета и идентификатор состояния блока не смешиваются. На диск пишется
версионированный реестр/семантическое соответствие, не случайный сетевой ID.
Палитры секций позволяют сохранить компактность при StateId(u32).

Для каждого блока/предмета отмечаем отдельно: известен реестру, отображается,
правильно размещается/сталкивается, работает механика, сохраняется, проверен
клиентом. Полные кубы включаются раньше сложных форм и block entities.
Плита — не полный куб, дверь должна открываться, печь — обрабатывать топливо.
Не выдаём неподдерживаемую игровую механику за выполненную загрузкой JSON.

Для инвентаря — один авторитетный владелец. При переносе PHP → Rust не держим
две одновременно изменяемые копии. Стековые ID, атомарные транзакции,
повторные запросы и отказ операции тестируются до крафта/контейнеров.

## Генерация, близкая к ваниле

Pumpkin остаётся основным кандидатом для отдельного интеграционного прототипа
генерации: адаптировать связанный конвейер биомов/шумов/поверхности/структур,
а не выдернуть один файл noise. Решение о переносе принимаем после сборки,
сравнения данных и проверки условий лицензии/происхождения исходников.
Сейчас Pumpkin worldgen НЕ включён в MPECore.

Нужен интерфейс WorldGenerator с seed, generator_id, generator_version,
настройками измерения и детерминированным доступом к соседним чанкам.
Эти параметры сохраняются в карте. Старый FlatGenerator остаётся отдельным
профилем для существующих тестовых карт; новая генерация включается в новой.

Два разных уровня качества: «похоже на ваниль» и «совпадает с официальным
Bedrock заданной версии по seed». Второе доказывается эталонными мирами:
высоты/биомы, пещеры/руды, координаты структур и содержимое контейнеров,
включая отрицательные координаты и края чанков. Не обещаем Bedrock seed parity
только потому, что сторонний генератор умеет принимать Bedrock-клиент.
Первый обычный Overworld может быть явно маркирован vanilla-like; точность
по seed и расширенные структуры — отдельные критерии, а не скрытая подмена.

## Нативный Rust и доступные плагины

Не останавливаем рабочую ветку ради полного переписывания всего одновременно.
Фиксируем форматы IPC/реестров, затем переносим NBT/кодеки/сессии в Rust
с дифференциальными тестами против текущего шлюза и реальными клиентами.
Цель: запуск без PHP/Node при отсутствии соответствующих скриптовых плагинов.
PHP Plugin API остаётся доступным без ручной компиляции плагинов.

Следующие возможности плагинов: права и команды, отменяемые события ДО
изменения мира, таймеры/асинхронные задания с квотами, устойчивые дескрипторы
игроков/мира и перезагрузка с очисткой обработчиков. Внешние процессы не
считаем песочницей; доверие/права/лимиты нужно реализовать явно.

## Как фиксировать результат каждого этапа

Отдельный commit/PR, воспроизводимый regression-тест, CI с конкретным SHA,
данные до/после и пользовательский плейтест. Непроверенная версия не становится
поддерживаемой автоматически. В отчётах различаем: тесты модели, реальные
кодеки, headless offline+encryption и официальный online-клиент.
